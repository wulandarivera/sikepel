1. Ringkasan Eksekutif
SIKEPEL adalah aplikasi web pelayanan administrasi kelurahan yang menggantikan alur kerja Excel + Microsoft Word Mail Merge dengan sistem terpusat berbasis database, template DOCX, penomoran terkontrol, dan arsip PDF. SIKEPEL v1 dirancang sejak awal untuk digunakan oleh banyak kelurahan dalam satu wilayah kecamatan melalui satu aplikasi dan satu katalog template surat global.
Tujuan utama v1 adalah menghasilkan prototype yang benar-benar berfungsi dan dapat dipresentasikan kepada pihak kecamatan, dengan arsitektur yang cukup aman untuk pilot terbatas setelah memperoleh otorisasi penggunaan data. Prototype tidak menggunakan watermark “DATA DEMONSTRASI” pada surat; pemisahan antara development, prototype, pilot, dan production dilakukan melalui environment dan kebijakan operasional, bukan melalui perubahan format surat.
Satu template DOCX per jenis surat dapat digunakan semua kelurahan melalui placeholder dinamis untuk kop, identitas kelurahan, pejabat, dan data surat.
Penduduk tidak berasal dari Dukcapil. Jika NIK belum tersimpan, operator menginput data dan sistem menyimpannya sebagai data lokal hasil pelayanan untuk penggunaan berikutnya.
Output resmi adalah PDF. DOCX hasil merge bersifat sementara dan dikonversi melalui Gotenberg + LibreOffice.
Nomor surat diberikan secara atomik pada saat penerbitan, bukan ketika form dibuka, sehingga mengurangi duplikasi dan nomor terbuang.
Setiap surat menyimpan snapshot data penduduk, organisasi, pejabat, template, dan nilai form pada saat diterbitkan sehingga cetak ulang tetap konsisten secara historis.
Arsitektur memakai abstraction layer untuk database, storage, authentication, dan PDF converter agar mudah dipindahkan dari cloud prototype ke server kecamatan.
2. Latar Belakang dan Tujuan
2.1 Latar belakang
Proses pelayanan saat ini mengandalkan input data melalui Excel dan Mail Merge ke Word. Masalah utama muncul ketika file Word atau koneksi Mail Merge berubah, nomor surat tidak sinkron, pegawai lain mengedit template, atau data berada pada beberapa salinan file yang berbeda. Ketergantungan pada file lokal juga membuat pengawasan, audit, cetak ulang, dan pelayanan ketika admin utama tidak berada di kantor menjadi sulit.
2.2 Tujuan produk
Menyediakan satu sistem pelayanan surat yang dapat digunakan bersama oleh kelurahan-kelurahan di satu kecamatan.
Memisahkan data, template, dan penomoran dari file Word yang dapat diedit operator.
Menghasilkan PDF yang konsisten dan siap print langsung dari browser.
Membangun arsip surat terstruktur dan dapat dicari kembali berdasarkan NIK, nama, jenis surat, nomor surat, tanggal, atau kelurahan.
Memastikan perubahan data penduduk atau pejabat tidak mengubah isi surat yang sudah diterbitkan.
Membuat prototype cloud yang mudah didemokan namun tetap portable ke infrastruktur pemerintah di masa depan.

6. Arsitektur Multi-Kelurahan
Setiap user memiliki village_id/kelurahan_id. Identitas tersebut berasal dari session dan digunakan server untuk membatasi query. Operator tidak memilih kelurahan secara bebas saat membuat surat. Super Admin Kecamatan menggunakan scope khusus untuk melihat atau mengelola tenant lain.
Login User
   ↓
Session { user_id, role, village_id }
   ↓
Authorization Middleware / Service Guard
   ↓
Query terfilter village_id
   ↓
Database + RLS
6.1 Aturan isolasi tenant
Setiap record sensitif yang bersifat lokal memiliki village_id.
Query operator selalu menggunakan village_id dari session, bukan nilai yang dikirim bebas oleh browser.
Supabase Row Level Security (RLS) menjadi lapisan tambahan terhadap authorization aplikasi.
Super Admin Kecamatan dapat memiliki scope lintas tenant yang eksplisit.
Template global tidak perlu memiliki village_id, kecuali kelak diperlukan override khusus.
7. Modul dan Requirement Fungsional
7.1 Requirement detail — Penduduk
Pencarian minimum mendukung NIK exact/partial dan nama partial.
NIK wajib 16 digit jika diisi; validasi format bukan verifikasi Dukcapil.
Jika tidak ditemukan, UI menawarkan “Tambah Penduduk & Lanjutkan Pelayanan”.
Setelah disimpan, penduduk langsung tersedia untuk form pelayanan aktif.
Perubahan master penduduk tidak memperbarui snapshot surat lama.
Histori surat penduduk hanya terlihat sesuai scope kelurahan.
Sistem harus menangani potensi duplikasi NIK pada tenant yang sama.
7.2 Requirement detail — Template
Format utama: DOCX.
Delimiter placeholder: ${placeholder}.
Template global terikat ke letter_type.
Upload template membuat versi baru, tidak menimpa versi lama.
Hanya satu versi aktif per letter_type untuk pemakaian default.
Template validator harus memindai placeholder dan membandingkan dengan field yang tersedia.
Template tidak dapat dihapus jika masih direferensikan surat terbit; hanya dapat dinonaktifkan/diarsipkan.
Template harus mendukung placeholder pada body, tabel, header, dan footer sejauh engine memungkinkan.
8. Workflow Pelayanan Surat
8.1 Happy path
1. Operator login
2. Sistem menetapkan tenant dari session
3. Operator pilih “Buat Pelayanan”
4. Pilih jenis surat
5. Cari NIK / nama
6a. Jika ada → pilih penduduk
6b. Jika tidak ada → input → simpan penduduk
7. Isi field khusus surat
8. Simpan draft / Preview
9. Generate preview PDF sementara tanpa nomor final atau dengan watermark DRAFT internal
10. Operator periksa
11. Klik TERBITKAN
12. Server validasi ulang
13. Database mengalokasikan nomor atomik
14. Snapshot data dibuat
15. DOCX final dirender dari template aktif
16. Gotenberg mengonversi DOCX → PDF
17. PDF di-upload ke storage
18. Record surat menjadi ISSUED
19. Operator melihat PDF final dan dapat print/download
8.2 Ketika konversi PDF gagal setelah nomor dialokasikan
Sistem tidak boleh diam-diam memberikan nomor baru tanpa jejak. Implementasi yang direkomendasikan adalah menyimpan status GENERATING/ISSUE_PENDING setelah nomor dialokasikan. Jika converter gagal, record tetap memiliki nomor yang sudah dicadangkan dan dapat di-retry dengan idempotency key. Setelah berhasil, status menjadi ISSUED. Jika diperlukan pembatalan permanen, nomor tersebut tetap tercatat sebagai VOID/CANCELLED sesuai kebijakan nomor surat.
9. Lifecycle Surat
9.1 Immutability
Surat ISSUED tidak diedit in-place.
Perubahan substansial setelah terbit dibuat sebagai pembatalan + surat baru, atau mekanisme revisi yang mempunyai record baru.
Cetak ulang menggunakan snapshot dan template_version_id yang direkam saat penerbitan.
Audit log menyimpan alasan pembatalan/revisi.
10. Sistem Template DOCX dan Placeholder
10.1 Sumber nilai placeholder
10.2 Aturan placeholder
Nama placeholder lowercase snake_case.
Tidak boleh mengandung spasi.
Placeholder global yang sama harus memiliki arti yang konsisten di semua jenis surat.
Field khusus surat didefinisikan di letter_form_fields.
Placeholder yang tidak dikenal menyebabkan template gagal diaktifkan, kecuali secara eksplisit ditandai optional.
Nilai null harus memiliki strategi: kosong, fallback, atau block penerbitan sesuai definisi field.
Formatter dipisahkan dari data mentah, misalnya tanggal_lahir_raw dan tanggal_lahir_formatted tidak perlu keduanya disimpan jika dapat dihasilkan deterministik.
10.3 Template versioning
Surat Domisili
  ├── Template v1 — inactive
  ├── Template v2 — inactive
  └── Template v3 — ACTIVE

Surat yang diterbitkan menggunakan v2 tetap menyimpan template_version_id=v2 untuk cetak ulang/audit.
11. Penomoran Surat
11.1 Kunci counter
Default counter key: village_id + letter_type_id + year. Struktur ini dapat diperluas ke month, classification_code, atau sequence_scope jika aturan kecamatan berbeda.
number_counters
- village_id
- letter_type_id
- year
- last_sequence
- updated_at

UNIQUE(village_id, letter_type_id, year)
11.2 Atomic allocation
Alokasi nomor harus dilakukan di server/database transaction.
Frontend tidak boleh menghitung nomor berikutnya.
Dua operator yang menerbitkan bersamaan harus menerima sequence berbeda.
Format nomor dibuat setelah sequence didapat.
Manual adjustment hanya untuk role khusus dan wajib audit reason.
11.3 Format nomor
Contoh konfigurasi:
{kode_surat}/{sequence_padded}/{kode_kelurahan}/{bulan_romawi}/{tahun}

Contoh hasil:
470/001/KEL/IX/2026

15.1 Requirement converter
Service converter tidak boleh diekspos sebagai endpoint publik tanpa autentikasi pada konfigurasi pilot/production.
Request harus memiliki timeout dan retry terbatas.
Ukuran DOCX/PDF harus dibatasi.
Converter harus menerima request id/idempotency context untuk tracing.
Font yang digunakan template harus tersedia pada image/container converter.
Preview dan final menggunakan pipeline yang sama agar layout konsisten.

17. Keamanan, Privasi, dan Isolasi Data
17.1 Baseline keamanan
Semua trafik menggunakan HTTPS.
Credential rahasia hanya berada di environment variable server.
Service role key tidak pernah dikirim ke browser.
Password dikelola provider Auth; aplikasi tidak menyimpan plaintext password.
RLS diterapkan pada tabel sensitif bila akses langsung Supabase digunakan.
Tenant scope wajib pada users, residents, letters, officials, counters, dan audit terkait.
Rate limiting diterapkan untuk login dan endpoint berat seperti generate PDF.
PDF converter menerima request hanya dari backend yang terautentikasi.
Audit event untuk perubahan permission, penomoran, template, pejabat, dan pembatalan surat.
Data riil digunakan hanya setelah ada otorisasi operasional dari instansi; sistem tidak memerlukan watermark demo untuk tetap membedakan fase proyek.
17.2 Data minimization
Jenis surat hanya meminta field yang benar-benar diperlukan. Field sensitif tidak perlu ditampilkan pada dashboard/list jika tidak dibutuhkan. NIK pada log teknis sebaiknya dimasking; NIK penuh hanya tampil pada konteks pelayanan yang berwenang.
18. Audit Log dan Observabilitas
18.1 Logging teknis
Gunakan correlation/request ID.
Jangan log PDF bytes atau DOCX contents.
Mask credential, token, NIK, dan payload sensitif.
Error converter harus dapat ditelusuri tanpa menyimpan isi dokumen pada log.

23. Acceptance Criteria SIKEPEL v1
PASS jika: Operator Kelurahan A tidak dapat melihat penduduk dan arsip Kelurahan B.
PASS jika: Satu template global Surat Domisili dapat menghasilkan kop dan pejabat berbeda sesuai user tenant.
PASS jika: Jika NIK belum ada, operator dapat menambahkan penduduk dan melanjutkan pelayanan tanpa mengulang input.
PASS jika: Dua operator menerbitkan surat bersamaan tanpa nomor sequence duplikat.
PASS jika: Surat yang telah diterbitkan dapat dicetak ulang dengan isi historis yang sama meskipun master penduduk/pejabat berubah.
PASS jika: Upload template baru menghasilkan versi baru dan tidak mengubah surat lama.
PASS jika: Placeholder yang tidak dikenal terdeteksi sebelum template diaktifkan.
PASS jika: Generate surat menghasilkan PDF yang dapat dipreview, didownload, dan diprint.
PASS jika: Kegagalan converter dapat di-retry tanpa mendapatkan nomor resmi baru.
PASS jika: Aksi terbit, batal, ubah template, ubah pejabat, dan ubah role tercatat pada audit log.
PASS jika: PDF dan template tidak memiliki public URL permanen tanpa authorization.
PASS jika: Aplikasi dapat dideploy melalui GitHub → Vercel dan terhubung ke Supabase + Cloud Run melalui environment variables.
